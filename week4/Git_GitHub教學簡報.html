上課前先安裝 Git 與 GitHub CLI

$ brew install git

Git 與 GitHub 是兩個不同層次

Git

安裝在電腦上的版本控制工具。即使沒有網路，也能建立 commit、切換 branch、查看歷史。

GitHub

託管 Git repository 的線上平台。它增加備份、分享、Issue、Pull Request 與 code review。

小例子：你可以只用 Git 管理自己的作業；當你要和組員交換 commit，才需要 GitHub 這類遠端平台。

範例專案：建立第一個 repository

$ mkdir campus-eats
$ cd campus-eats
$ git init
Initialized empty Git repository in .../campus-eats/.git/
$ printf "# Campus Eats\n" > README.md
$ git status
git init 的輸入：一個普通資料夾。
它做的事：新增隱藏的 .git 目錄，用來保存版本資料。
輸出：原本檔案不會被改寫；資料夾開始具備 Git 版本歷史。

先問 Git：目前發生了什麼？

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present
  • 1
    On branch main現在站在 main 分支。
  • 2
    No commits yet版本歷史目前是空的。
  • 3
    UntrackedGit 看到 README.md，但你還沒決定要不要追蹤它。
習慣：不確定下一步時，先執行 git status。它只讀取狀態，不會改變檔案。

git add 是挑選下一張快照

$ git add README.md
$ git status
Changes to be committed:
        new file:   README.md

git add README.md 把當下這份 README.md 的內容放進暫存區。

容易誤會：add 不是「以後自動追蹤所有修改」。如果 add 之後又改了檔案，要再 add 一次，新的內容才會進入下一個 commit。
小問題：同時改了 README.md 和 menu.txt，但這次只想提交 README.md，怎麼做？
git add README.md。暫存區讓一次 commit 只包含相關修改。

git commit 把暫存區存成版本

$ git commit -m "docs: add project introduction"
[main (root-commit) a1b2c3d] docs: add project introduction
 1 file changed, 1 insertion(+)
 create mode 100644 README.md

$ git log --oneline
a1b2c3d docs: add project introduction
  • 1
    -m 後面是這個版本的說明。
  • 2
    a1b2c3d 是示意的 commit ID。Git 用它識別特定版本；你的實際 ID 會不同。
  • 3
    好的訊息說明「完成了什麼」。fix: correct lunch price 比 update 更容易理解。

第二次提交：新增第一筆菜單資料

$ printf "台大牛肉麵,120\n" > menu.csv
$ git status
$ git add menu.csv
$ git diff --staged
+台大牛肉麵,120

$ git commit -m "data: add first restaurant"
git diff：看尚未放進暫存區的已追蹤檔案修改。
git diff --staged：看下一個 commit 實際會包含什麼。
這一頁做的是新增：先建立 menu.csv，內容是牛肉麵 120 元。下一頁才會修改這個價格。

第三次提交：把 120 修改成 130

現在 menu.csv 已經存在。先在終端機開啟檔案，修改後再讓 Git 比較前後差異。

$ nano menu.csv

# 改成：
台大牛肉麵,130

# 儲存：Control + O，再按 Enter
# 離開：Control + X

$ git diff
-台大牛肉麵,120
+台大牛肉麵,130
  • 1
    輸入：已經被 Git 追蹤的 menu.csv，原本價格是 120。
  • 2
    nano menu.csv在終端機中開啟文字編輯器。用方向鍵移動游標，把 120 刪掉並輸入 130。
  • 3
    儲存與離開Control + O 寫入檔案，Enter 確認檔名，Control + X 回到終端機。
  • 4
    git diff減號是舊內容，加號是新內容。此時 Git 已看到價格變更，但還沒有建立 commit。
$ git add menu.csv
$ git diff --staged
$ git commit -m "data: correct lunch price"

2

本機 commit

add 後 commit，版本先存在你的電腦。

3

push

把本機已有的 commit 上傳到遠端。

4

GitHub 顯示

組員可以查看、clone 或提出 review。

因果關係：如果你只修改檔案但沒有 commit，git push 沒有新版本可以上傳。

把本機 repository 連到 GitHub

  1. 在 GitHub 建立空的 repository，例如 campus-eats。
  2. 複製它的 HTTPS 或 SSH URL。
  3. 在本機加入名為 origin 的遠端位置。
$ git remote add origin https://github.com/YOUR-NAME/campus-eats.git
$ git remote -v
$ git push -u origin main
origin：遠端 URL 的慣用別名。-u：記住本機 main 對應 origin/main，之後通常只要輸入 git push。

四個遠端指令，各自搬動不同內容

指令輸入做的事結果
git clone URL遠端 repository第一次下載完整專案、歷史與遠端設定新的本機資料夾
git fetch遠端新 commit下載遠端資訊，但先不改目前工作分支可先比較差異
git pull遠端新 commit先 fetch，再整合到目前分支本機分支更新
git push本機新 commit把本機分支的 commit 上傳遠端分支更新

多人協作前，先同步再開始改

1

確認工作目錄

git status
不要帶著不明修改同步。

2

取得最新版本

git pull --ff-only
只接受可直接前進的更新。

3

開始修改

完成一件小事後 add、commit。

4

上傳 commit

git push
讓遠端取得本機新版本。

--ff-only：如果本機與遠端各自有新 commit，Git 會停止並請你處理分岔，不會自動產生你沒預期的 merge commit。

練習二：判斷該用哪個指令

A. 第一次把組員的 GitHub 專案完整下載到電腦
git clone URL
B. 想先知道遠端有沒有更新，但暫時不改目前檔案
git fetch
C. 已經 commit，要把新版本送到 GitHub
git push
D. 取得遠端更新並整合到目前分支
git pull

push 被拒絕：遠端已有你沒有的 commit

$ git push
! [rejected] main -> main (non-fast-forward)
error: failed to push some refs
hint: Updates were rejected because the remote contains work
hint: that you do not have locally.

Git 不敢直接上傳，因為那可能讓遠端看不到組員已經 push 的 commit。

先做：git pull --ff-only。若不能直接前進，代表本機與遠端都各自有新 commit。
不要直接：git push --force。它可能覆寫遠端歷史。

branch：從同一個 commit 開始，之後各自前進

把 C 當成目前的穩定版本。建立 feature/menu 時，兩個 branch 一開始都指向 C。

A
B
C
main 指向 C穩定版本留在這裡
A、B、C 是兩個 branch 共有的歷史
feature/menu 也先指向 C此時還沒有新的 commit
D
E
feature/menu 指向 E新功能的 commit 只讓它往前
  • 1
    起點：main 指向 C。C 保存目前穩定的檔案內容。
  • 2
    建立 branch：Git 新增 feature/menu 這個名稱。它先指向同一個 C，不會另外複製一個專案資料夾。
  • 3
    在 feature 上 commit：新增 D、E。feature/menu 移到 E，main 仍然停在 C。
為什麼要這樣做：新功能還沒完成時，main 仍保留可用版本；完成後再 merge。

建立功能分支，完成一個小改動

$ git switch -c feature/add-vegetarian
Switched to a new branch 'feature/add-vegetarian'
$ echo "蔬食自助餐,90" >> menu.csv
$ git add menu.csv
$ git commit -m "data: add vegetarian option"
$ git log --oneline --graph --decorate --all
switch -c：從目前 commit 建立新分支，並立刻切換過去。
為什麼這裡用 echo：echo "文字" 預設會在結尾換行；printf "文字" 則要自己加上 \n。這裡的 >> 會把新的一行加到 menu.csv 最後，不會覆蓋原本內容。
輸出：main 仍指向原本版本；feature 分支前進到新 commit。
命名：用短而具體的名稱，例如 fix/wrong-price。

把功能分支整合回 main

$ git switch main
$ git merge feature/add-vegetarian
Updating ...
Fast-forward
$ git log --oneline --graph --decorate --all
  • 1
    先切回「要接收修改」的 main。
  • 2
    執行 merge，指定「要被合進來」的功能分支。
  • 3
    Fast-forwardmain 在功能開發期間沒有新增 commit，因此只要把 main 指標向前移動。
檢查：merge 後執行測試、查看 git status，再 push 更新遠端 main。

conflict：Git 不知道同一處該保留哪個版本

main

台大牛肉麵,130
組員把價格改成 130。

feature/discount

台大牛肉麵,110
你把同一行改成優惠價 110。

Git 能確定：兩個分支都改了同一行。
Git 無法確定：130 和 110 哪個才符合團隊的真實需求。
所以 conflict 不是程式壞掉。它是 Git 停下來，要求人決定最後內容。

conflict 檔案中的兩個版本

Git 把兩個版本都放進 menu.csv，等你決定最後要留下哪一個。

<<<<<<< HEAD
台大牛肉麵,130
=======
台大牛肉麵,110
>>>>>>> feature/discount
  • 1
    目前的 mainHEAD 下方到分隔線以前，是 main 的內容：130 元。
  • 2
    要合進來的 feature/discount分隔線下方到最後一行以前，是功能分支的內容：110 元。

假設團隊決定保留優惠價 110：
用編輯器刪掉 130 和標記，只留下右邊這一行。

台大牛肉麵,110

修改檔案後，完成這次 merge

你已經在編輯器把 menu.csv 改成最後要保留的內容。接下來才回到終端機。

$ git add menu.csv
$ git status
All conflicts fixed but you are still merging.

$ git commit -m "merge: resolve lunch price conflict"
  • 1
    git add menu.csv把修改後的內容放進暫存區。Git 也會把這個檔案視為已解決。
  • 2
    git status如果看到上面的訊息，表示檔案衝突都已處理，但 merge 還沒完成。
  • 3
    git commit建立這次 merge 的 commit，整個 merge 到這裡完成。
如果決定不合併：git merge --abort 取消這次 merge。

Pull Request 是「請團隊審查這組 commit」

1

Push branch

把功能分支上傳到 GitHub。

2

Open PR

說明問題、修改內容與測試方式。

3

Review

組員閱讀 diff、留言並要求修改。

4

Merge

通過檢查後，把 branch 整合進 main。

PR 描述至少回答：為什麼要改？改了什麼？別人如何驗證？

一輪完整的 GitHub Flow

  1. 切回 main，取得最新版本。
  2. 從 main 建立功能分支。
  3. 完成小範圍修改，分成清楚的 commit。
  4. push branch，開 Pull Request。
  5. 回應 review，測試通過後 merge。
$ git switch main
$ git pull --ff-only
$ git switch -c feature/add-map
# 修改、測試
$ git add map.md
$ git commit -m "docs: add restaurant map"
$ git push -u origin feature/add-map

修正錯誤前，先判斷 commit 是否已分享

情況較安全的工具原因
工作目錄改壞，尚未 addgit restore 檔名丟棄尚未暫存的修改；執行前先確認真的不要
已 add，想移出暫存區git restore --staged 檔名保留工作內容，只取消這次暫存
錯誤 commit 已 pushgit revert COMMIT建立相反修改的新 commit，不改寫共享歷史
尚未分享的本機歷史amend、reset 或 rebase可能改寫 commit；先備份並確認影響範圍
高風險：reset --hard 會丟棄工作內容。不要把它當成萬用復原按鈕。

你想回答的問題指令會不會改東西
現在有哪些修改？git status、git diff不會，只讀取
下一個 commit 要放什麼？git add 檔名、git diff --stagedadd 會改暫存區
保存一個版本？git commit -m "訊息"新增 commit
查看版本歷史？git log --oneline --graph --all不會，只讀取
與 GitHub 同步？git fetch、git pull、git push下載、整合或更新遠端
隔離一個新功能？git switch -c branch建立並切換分支

今天帶走的核心模型

一個 commit

先用 add 挑選相關修改，再用 commit 留下可理解的版本與訊息。

兩個 repository

本機先保存 commit；push 與 pull 才讓本機和 GitHub 交換版本。

多條 branch

新功能在獨立分支完成。PR 讓團隊先看 diff、討論、測試，再合併。

最重要的習慣：小步修改、先看 status、提交前看 diff、同步前確認工作目錄。
