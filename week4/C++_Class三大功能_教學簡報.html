C++ Class 三大功能
封裝、繼承與多型

程式設計小老師｜Week 4

從「保護物件狀態」，到「用共同介面操作不同物件」

先提醒學生：這堂課假設已經看過 class、建構子與 private/public。今天重點是三個設計能力如何解決真實問題。

今天的路線

每一站都從問題開始，再看語法、執行流程與練習。

封裝

把規則守在 class 裡，避免物件進入不合法狀態

繼承

表達 is-a 關係，沿用基底類別提供的介面

多型

用同一個呼叫方式，執行不同實際型別的行為

整合挑戰

獨立設計可擴充的角色系統

閱讀順序：輸入是什麼 → 這段程式做什麼 → 為什麼需要 → 輸出與下一步。

三種常見問題，對應三個能力

狀態被改壞

外部直接把餘額設成負數。封裝把修改集中到會檢查規則的方法。

共同資料重複

每種員工都重寫姓名與編號。繼承讓衍生類別沿用基底部分。

型別越多，判斷越長

每新增一種付款方式，就多一段 if。多型把差異交回各類別。

先做設計判斷，再選語法。不是看到 class 就一定要同時使用繼承與多型。

先對齊四個基本名詞

class Student {
    int score_;
public:
    int score() const;
};

Student alice;
  • 1
    classStudent 是型別的設計圖。
  • 2
    objectalice 是依照設計圖建立的物件。
  • 3
    memberscore_ 與 score() 都屬於 Student。
  • 4
    public interface類別外被允許呼叫的公開功能。
FIRST PART
封裝
Encapsulation

這一站要回答

  1. 為什麼欄位不能全部 public？
  2. 公開方法如何保護規則？
  3. getter／setter 應該怎麼設計？

公開欄位讓每一段外部程式都能繞過規則

class BankAccount {
public:
    int balance = 0;
};

BankAccount a;
a.balance = -500;
  • 1
    輸入：任何整數都能被指定給 balance。
  • 2
    問題：沒有一個固定位置檢查「餘額不可為負」。
  • 3
    結果：物件進入不合法狀態，後面的函式只能被迫補救。
封裝不是加密。它是由編譯器限制哪些程式碼可以直接存取成員。

private 保存狀態，public 提供受控操作

class BankAccount {
private:
    int balance_ = 0;

public:
    bool deposit(int amount);
    bool withdraw(int amount);
    int balance() const;
};
資料：類別外的一般程式碼無法直接修改 balance_；修改集中在類別提供的方法。
介面：外部只能提出「存款」或「提款」要求。
效果：金額檢查集中在兩個方法，不必散落在每個呼叫端。

建構子守住物件的第一個狀態

class BankAccount {
    std::string owner_;
    int balance_;
public:
    BankAccount(std::string owner)
        : owner_(owner), balance_(0) {}
};
  • 1
    輸入：建立帳戶時傳入 owner。
  • 2
    初始化列表：在進入建構子本體前，直接建立兩個成員。
  • 3
    輸出：每個新帳戶都有擁有者，且餘額從 0 開始。
為什麼需要：若物件一建立就可能不合法，後面的 public 方法再安全也救不了初始狀態。

deposit 先檢查，再改變狀態

bool BankAccount::deposit(int amount) {
    if (amount <= 0) {
        return false;
    }
    balance_ += amount;
    return true;
}
1

輸入

呼叫端提出 amount。

2

檢查

0 或負數直接失敗。

3

修改

只有合法金額才增加餘額。

回傳值：true 表示狀態真的有改變；false 表示餘額保持原值。

withdraw 同時檢查金額與餘額

bool BankAccount::withdraw(int amount) {
    if (amount <= 0 || amount > balance_) {
        return false;
    }
    balance_ -= amount;
    return true;
}
呼叫前呼叫結果
100withdraw(40)true，餘額 60
60withdraw(80)false，仍為 60
60withdraw(0)false，仍為 60
因果關係：失敗分支先 return，所以減法只可能在兩個條件都合法時執行。

getter 與 setter 不是越多越好

無條件 setter

void setBalance(int value) {
    balance_ = value;
}

外部仍能寫入 -500，private 只剩形式。

符合需求的方法

bool deposit(int amount);
bool withdraw(int amount);
int balance() const;

方法名稱直接表達允許的操作與規則。

設計問題：外部真正需要做什麼？如果不需要任意設定餘額，就不應提供 setBalance。

尾端 const 表示這個方法只讀取物件

int BankAccount::balance() const {
    return balance_;
}

const BankAccount savings("Amy");
std::cout << savings.balance();
  • 1
    作用對象：點號左邊的帳戶物件。
  • 2
    承諾：這個方法不透過 this 修改物件成員。
  • 3
    結果：const 物件也能呼叫它；編譯器會阻止意外修改。

練習一：預測每次呼叫後的餘額

BankAccount a("Ming");
std::cout << a.deposit(100) << ' ';
std::cout << a.withdraw(30) << ' ';
std::cout << a.withdraw(90) << ' ';
std::cout << a.balance();
請先寫下四個輸出，再說明第三次呼叫為什麼不改變餘額。
答案：1 1 0 70。第三次要提領 90，但當時只有 70，所以方法回傳 false，並在減法前結束。

練習二：Temperature 的合法範圍

攝氏溫度不能低於絕對零度 -273.15°C。完成建構子與兩個只讀方法。

class Temperature {
    double celsius_;
public:
    explicit Temperature(double celsius);
    double celsius() const;
    double fahrenheit() const;
};
  • 1
    非法建構值改存 -273.15。
  • 2
    華氏公式：攝氏 × 9 / 5 + 32。
  • 3
    測試 -300、0、100。
參考核心：celsius_(celsius < -273.15 ? -273.15 : celsius)。兩個讀取方法尾端都要有 const。

練習三：自己設計公開介面

設計 InventoryItem。名稱、單價、庫存量都放在 private。

補貨

數量必須大於 0；成功才增加庫存，並回傳 true。

出售

數量必須大於 0 且不可超過庫存；失敗時庫存不變。

讀取

提供庫存量與總價。總價 = 單價 × 庫存量。

至少列出六個邊界測試
補貨 0、補貨負數、補貨 1、出售 0、出售負數、出售等於庫存、出售超過庫存。每次都檢查回傳值與庫存是否正確。

繼承
Inheritance

這一站要回答

  1. 什麼關係適合使用繼承？
  2. 衍生類別能沿用什麼？

不同類別可能重複同一組共同資料

Student

std::string name_;
int id_;
int credits_;

學生另外需要學分。

Teacher

std::string name_;
int id_;
std::string office_;

老師另外需要辦公室。

觀察：兩者都是 Person，都需要 name 與 id。這個 is-a 關係才是考慮繼承的主要理由。

public inheritance 表達「衍生類別是一種基底類別」

class Person {
public:
    std::string name() const;
};

class Student : public Person {
public:
    int credits() const;
};
  • 1
    Person：base class，中文常稱基底類別。
  • 2
    Student：derived class，中文常稱衍生類別。
  • 3
    輸出能力：Student 物件可使用 Person 的 public name()，也有自己的 credits()。

建立衍生物件時，基底部分先建立

Student::Student(std::string name, int id,
                 int credits)
    : Person(name, id),
      credits_(credits) {
}
1

Person

先初始化 name 與 id。

2

Student 成員

再初始化 credits_。

3

函式本體

最後執行大括號內容。

為什麼：Student 物件裡先要有完整可用的 Person 部分，才能建立 Student 自己的部分。

public、protected、private 在繼承中的差別

基底成員Person 自己Student 成員函式main 等外部程式
public可直接使用可直接使用可透過物件使用
protected可直接使用可直接使用不可直接使用
private可直接使用不可直接使用不可直接使用
通常的安全選擇：資料仍放 private。若衍生類別需要能力，提供 protected 或 public 方法，讓基底類別繼續守住規則。

衍生類別沿用基底類別已完成的功能

Student s("Amy", 1001, 24);

std::cout << s.name();
std::cout << s.id();
std::cout << s.credits();
  • 1
    name() 與 id()定義在 Person，Student 不必重寫。
  • 2
    credits()只屬於 Student 的功能。
  • 3
    輸出：Amy、1001、24。
目前只證明「沿用介面」。同名函式是否能依實際物件自動選擇，還要等多型的 virtual。

is-a 用繼承，has-a 通常用組合

is-a

Student 是一種 Person。凡是需要 Person 的地方，Student 應該也合理。

class Student : public Person {};

has-a

Car 有一顆 Engine，但 Car 不是一種 Engine。把 Engine 當成成員。

class Car {
    Engine engine_;
};
不要只為了少寫幾行就繼承。如果語意不是 is-a，組合通常更清楚。

練習四：哪些關係適合 public inheritance？

關係你的判斷參考答案
Circle 與 Shapeis-a / has-a？is-a：Circle 是一種 Shape
Car 與 Engineis-a / has-a？has-a：Car 有 Engine
Teacher 與 Personis-a / has-a？is-a：Teacher 是一種 Person
Library 與 Bookis-a / has-a？has-a：Library 收藏 Book
檢查方式：把句子讀成「A 是一種 B」。若語意明顯不合理，就不該用 public inheritance。

練習五：完成 ElectricCar 的建構子

class Vehicle {
public:
    Vehicle(std::string brand);
};

class ElectricCar : public Vehicle {
    int battery_;
public:
    ElectricCar(std::string brand, int battery);
};
初始化列表要先指定哪兩個部分？
ElectricCar::ElectricCar(std::string brand, int battery)
  : Vehicle(brand), battery_(battery) {}
先呼叫 Vehicle 建構子，再初始化 ElectricCar 自己的 battery_。

多型
Runtime polymorphism

這一站要回答

  1. virtual 改變了什麼？
  2. 為什麼要用基底參考或指標？
  3. 抽象類別如何定義共同介面？

多型：同一個呼叫，依實際型別執行

共同呼叫

shape.area()

→

Circle

π × r²

或

Rectangle

width × height

或

Triangle

base × height ÷ 2

呼叫端只依賴 Shape 的共同介面。新增 Triangle 時，原本的面積列印函式不必增加 if 判斷。

沒有 virtual 時，基底參考只看宣告型別

class Animal {
public:
    void speak() const { std::cout << "Animal"; }
};
class Dog : public Animal {
public:
    void speak() const { std::cout << "Woof"; }
};
Dog dog;
const Animal& a = dog;
a.speak();

Animal
原因：a 的型別是 Animal 參考，而 Animal::speak 沒有宣告 virtual。

virtual 允許執行實際物件的版本

class Animal {
public:
    virtual void speak() const {
        std::cout << "Animal";
    }
};

void Dog::speak() const override {
    std::cout << "Woof";
}
  • 1
    virtual要求透過基底參考或指標呼叫時，查看實際物件型別。
  • 2
    override要求編譯器確認函式簽章真的覆寫基底 virtual 函式。
  • 3
    同樣呼叫：a.speak() 現在輸出 Woof。

基底參考把「實際是誰」保留下來

void makeSpeak(const Animal& animal) {
    animal.speak();
}

Dog dog;
makeSpeak(dog);

輸入

Dog 物件，以 Animal const reference 接收。

→

virtual dispatch

執行期查到實際物件是 Dog。

輸出：呼叫 Dog::speak，印出 Woof。函式本身不需要知道 Dog 這個型別名稱。

純虛擬函式只規定介面，不提供預設答案

class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};
  • 1
    = 0area 是 pure virtual function，中文常稱純虛擬函式。
  • 2
    Shape 變成抽象類別不能直接建立 Shape s;。
  • 3
    衍生類別責任想成為可建立的具體 Shape，就要覆寫 area。

可能透過基底指標刪除物件時，解構子必須是 virtual

class Shape {
public:
    virtual ~Shape() = default;
};

Shape* p = new Circle(2.0);
delete p;
  • 1
    輸入：基底指標實際指向 Circle。
  • 2
    virtual 解構：delete 先執行 Circle 解構，再執行 Shape 解構。
  • 3
    實務：通常用 std::unique_ptr<Shape>，避免手動 delete。
沒有 virtual 的風險：透過基底指標刪除衍生物件會產生 undefined behavior，也就是 C++ 不保證結果。

用值存成基底物件，衍生部分會被切掉

Dog dog;

Animal copied = dog;
copied.speak();

// copied 已是獨立的 Animal 物件
object slicing：把 Dog 以值複製進 Animal，只保留 Animal 那一部分。
要保留多型：使用 Animal&、Animal*，或 std::unique_ptr<Animal>。
判斷重點：不是「有 virtual 就永遠多型」；儲存與傳遞方式也必須保留實際物件。

整合範例第一步：Shape 規定共同問題

class Shape {
public:
    virtual double area() const = 0;
    virtual std::string name() const = 0;
    virtual ~Shape() = default;
};
  • 1
    area()每種圖形都必須回答面積。
  • 2
    name()每種圖形都必須提供名稱。
  • 3
    沒有指定公式因為圓形與矩形的計算方式不同。

整合範例第二步：各類別提供自己的公式

Circle

class Circle : public Shape {
    double radius_;
public:
    Circle(double r) : radius_(r) {}
    double area() const override {
        return 3.14159 * radius_ * radius_;
    }
    std::string name() const override { return "圓形"; }
};

Rectangle

class Rectangle : public Shape {
    double width_, height_;
public:
    Rectangle(double w, double h)
        : width_(w), height_(h) {}
    double area() const override {
        return width_ * height_;
    }
    std::string name() const override { return "矩形"; }
};

整合範例第三步：一個容器保存不同圖形

std::vector<std::unique_ptr<Shape>> shapes;
shapes.push_back(std::make_unique<Circle>(2.0));
shapes.push_back(std::make_unique<Rectangle>(3.0, 4.0));

for (const auto& shape : shapes) {
    std::cout << shape->name()
              << ": " << shape->area() << '\n';
}
輸入：容器裡有 Circle 與 Rectangle，但元素型別統一為 unique_ptr<Shape>。
執行：每次迴圈都呼叫相同的 name() 與 area()。
輸出：圓形約 12.5664；矩形 12。

練習六：預測 virtual 呼叫

void printArea(const Shape& shape) {
    std::cout << shape.name()
              << ' ' << shape.area() << '\n';
}

Circle c(1.0);
Rectangle r(2.0, 5.0);
printArea(c);
printArea(r);
同一個函式為什麼能算出兩種公式？
輸出：圓形約 3.14159、矩形 10。參數是 Shape const reference，沒有複製；virtual 依實際物件分別呼叫 Circle::area 與 Rectangle::area。

練習七：付款方式的共同介面

設計抽象類別 PaymentMethod，讓 Cash 與 CreditCard 各自實作 pay。

class PaymentMethod {
public:
    virtual bool pay(int amount) = 0;
    virtual ~PaymentMethod() = default;
};
  • 1
    Cash：現金不足就 false；成功則扣除現金。
  • 2
    CreditCard：超過剩餘額度就 false；成功則增加已用額度。
  • 3
    測試：用 PaymentMethod& 寫一個 checkout 函式。
完成條件：checkout 不使用 if 判斷付款型別；新增付款方式時，不修改 checkout。

三大功能的常見錯誤

看到的情況原因修正方向
private 欄位都有無條件 setter外部仍可把狀態改壞提供符合需求的操作，並集中檢查
Car 繼承 Engine把 has-a 誤寫成 is-a將 Engine 改成 Car 的成員
基底參考呼叫到基底版本基底函式沒有 virtual基底加 virtual，衍生版本加 override
多型放進 vector 後失效用值儲存造成 object slicing存 unique_ptr<Base> 或 reference wrapper
透過 Base* 刪除衍生物件基底解構子不是 virtual將基底解構子設為 virtual

整合挑戰：可擴充的角色系統

設計 Character、Warrior 與 Mage。每新增角色，不修改戰鬥函式。

1

封裝

name_、hp_ 為 private。takeDamage 不讓 hp 低於 0。

2

繼承

Warrior 與 Mage 都 public 繼承 Character。

3

多型

Character 宣告純虛擬 attack()，兩種角色各自 override。

4

驗證

vector<unique_ptr<Character>> 依序呼叫 attack。

邊界測試：傷害 0、負傷害、傷害剛好等於 hp、超過 hp；再加入 Archer，確認原本迴圈完全不改。

三個能力，解決三種不同問題

封裝

把狀態設為 private，讓 public 方法先檢查，再決定是否修改。

繼承

用 public inheritance 表達 is-a，讓衍生類別沿用基底介面。

多型

基底 virtual 介面搭配參考或指標，依實際物件執行 override 版本。

設計順序：先確認物件必須守住的規則，再判斷 is-a 關係，最後確認呼叫端是否需要用共同介面操作不同型別。
